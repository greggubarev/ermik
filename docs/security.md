# Security model

To report a vulnerability privately, follow the [security policy](../SECURITY.md). Repository maintainers triage reports through GitHub Security Advisories; public Issues are for nonsensitive work.

The controller is trusted. It owns GitHub access, the state directory, workspace creation, checks, publication, and review records. The task command is untrusted and runs in a Docker container. The container receives the task checkout and the issue body, but no GitHub credential. It cannot authorize publication or merge by writing text into a file. The controller must validate the issue identity, permitted paths, changed files, check results, branch, and head commit before each external write.

## Credentials and permissions

- Keep `gh` credentials in the trusted host account only. Use repository-scoped, least-privilege access where possible. Do not bind-mount its home directory, `GH_CONFIG_DIR`, SSH keys, credential helpers, or token files into the worker container.
- [GitHub Free does not provide branch protection for private repositories](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule). A publisher credential with write access to the target repository may also push or merge `main` outside this program. Treat that host as fully trusted. For fork publication, configure `publish_repo` and `publish_token_env` together. The upstream `GH_TOKEN` needs Contents read, Issues write, and Pull requests write, without Contents write. The separate fork token needs Contents write on the fork. The controller checks the fork's exact parent and actively probes denied upstream ref creation and update under both credentials, plus successful fork ref creation under the fork credential. Repository `permissions.push` can reflect the account role instead of a narrow token; it is not the capability gate. [Private personal repositories grant collaborators write access](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository), so an extra account alone does not establish the boundary; use scoped credentials and prove the negative push case. The local review command is a workflow gate, not a GitHub permission boundary.
- Keep any provider credential separate from GitHub credentials. `worker_env` names host environment variables to pass to the container; leave it empty unless the task requires them. If a task runner needs a provider key and network access, it can potentially send that key or source content to an external service. Docker process separation is not a strong confidentiality boundary for a key intentionally supplied to a networked task. Limit the key's scope and cost, monitor usage, and avoid supplying sensitive repository data unless that exposure is acceptable.
- A user with access to the Docker daemon can usually gain broad host privileges. Protect the daemon socket and the controller account; consider rootless Docker where it fits the host setup.
- Restrict `config.json` to `0600` and state/workspace directories to `0700` under the controller account. Logs and status output should avoid tokens, full provider responses, private issue text, and unnecessary local paths.
- The controller marks each Docker container with its own state namespace, force-removes a named container on timeout, and removes remaining containers with that exact namespace before new work after a restart. Protect the state directory marker from other host users. This recovers from a stopped controller; it does not make a networked worker confidential against the selected provider or a compromised Docker host.

## Task and publication boundaries

- Treat issue bodies, comments, repository files, worker output, and check output as untrusted data. They cannot override the configured repository, maintainer, allowed paths, or approval rules.
- Require a narrow `Allowed paths` section in each issue. Reject absolute paths, traversal, `.git` changes, symlink escapes, and files outside the declared scope. Review the exact diff even after path validation.
- Run checks from the trusted configuration as argument arrays. A passing check establishes only what that command tested; it does not prove that a change is safe or meets the issue goal.
- The maintainer's `admit` command posts an approval comment bound to the issue number, exact body hash, and allowed path hash. The server checks the comment author against the configured maintainer before claiming work and before push. A ready label alone is insufficient. The maintainer and server can keep separate private state directories.
- Recheck GitHub state before push, PR creation, review, and merge. Bind each decision to the issue, branch, base, head SHA, and exact check result. On an ambiguous API response, reconcile remote state before retrying a write.
- The controller saves the execution image ID before the first container and publishes that ID in the draft PR. The broker verifies it against exact-head check evidence. A maintainer review compares the published ID to its locally configured image and runs checks by that exact ID. The review records the ordered check commands and image ID. Merge rejects a changed policy, replaced image, changed PR image declaration, or incomplete record before changing the PR. Review the current HEAD again after updating checks or the image. The PR body is a controller claim, not a cryptographic attestation; only trust it under the stated publisher credential boundary. Portable authenticated evidence remains separate roadmap work.
- In fork mode, the controller pushes task branches only to `publish_repo` using the fork token and creates PRs against `repo` using the upstream credential with an explicit fork owner. PR reconciliation and review verify that the head repository is the configured fork. Read-only `doctor` verifies the fork identity and parent but does not establish write permissions. Before publication, `run-once` and `poll` probe publication capabilities, including upstream refusal; the fork credential may receive 404 for a private upstream only after the exact fork parent was verified. A probe may create a disposable ref. Its intent records the exact repository, generated ref, and expected SHA in private controller state before the remote create request; it contains no token. The documented Linux controller syncs the intent file and directory before POST; Windows power-loss durability of the directory is unverified. On restart the controller must inspect that exact ref with the same scoped credential and delete it only while the SHA still matches. An unreadable or changed ref blocks cleanup and new publication until an operator reconciles it. GitHub's ref DELETE does not accept a SHA precondition, leaving a race if another actor updates the ref after the final read. Keep the state directory and its probe records across restarts and upgrades. The maintainer's merge credential needs Contents write on the upstream repository and stays separate from both controller credentials. For private upstream and fork repositories owned by different accounts, direct PR creation can fail because the upstream token cannot read the fork ref. A separate [PR broker](pr-broker.md) needs a credential that can read both repositories and create upstream PRs, but cannot write upstream Contents or merge; a broker holding the maintainer's broad credential does not establish the server-side permission boundary. On a disposable upstream branch, verify that both controller credentials cannot push or merge, and verify a successful fork push. Never test refusal by pushing to upstream `main`.
- Keep merge as an explicit maintainer action. A draft PR and successful local checks do not grant merge authority. The project does not rely on GitHub Actions or paid branch rules; the maintainer must enforce review and checks operationally.
- The maintainer merge command records its attempt before sending the request and reconciles GitHub state on retry. If the request outcome is uncertain and the PR still appears open, it will not send another request automatically. Inspect the PR, its branch, and the default branch before deciding on any further action. A failed post-merge check is recorded as incomplete and does not undo the merge.

## Release and operations

Before publishing a source release, run the [source release gate](release.md) against the reviewed commit and inspect its archive, manifest, and checksum. The gate scans the release tree and history for credentials, private data, local paths, logs, SQLite state, checkouts, and unexpected artifacts. `.gitignore` reduces accidental additions but does not remove tracked files or old commits. Stop publication and rotate an exposed credential if a secret is found; the release guide gives the full response. Keep third-party licenses and required notices with redistributed components and review the terms of any base image used by a task image. The source gate does not inspect a built image.

Use a disposable repository and credentials for the first end-to-end run. Exercise a successful task and negative cases: wrong repository or maintainer, changed issue body, out-of-scope file, failed check, changed base or head, interrupted publication, and repeated command. Confirm that no worker container can read the GitHub credential and that retries do not create a second PR or repeat a merge.
