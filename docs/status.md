# Local status and resource limits

## Optional outbound event digest

Set `ERMIK_DIGEST_URL` to an HTTPS webhook and `ERMIK_DIGEST_TOKEN` to its bearer credential in the trusted installation's environment. Keep both out of `config.json`, source control, worker environments, and command arguments. With neither variable set, delivery is disabled. Set both on either the controller installation, the maintainer installation, or both, then schedule `python3 -m ermik --config config.json send-digest` at least once a minute. The command is separate from execution and merge; a failed destination cannot hold their state lock or repeat their writes.

Each invocation sends at most one event. Controller events cover a new draft PR, blocked work, and a confirmed remote merge. The maintainer's validated decision trail covers a requested correction and completed post-merge verification. A delivery contains only the event name, Issue and PR numbers, and verified links under the configured repository. It does not include issue text, review notes, errors, logs, branches, or commit hashes. The command checks the remote Issue and PR relationship before sending; an unavailable remote check waits for a later invocation, while a confirmed identity mismatch suppresses that transition. Results report only a bounded status, event name, and Issue number.

Delivery state is stored privately in `state_dir/event-digest.json`. Successful delivery advances its event cursor and each decision journal's position; failures retry after a bounded backoff. HTTP 429 honors `Retry-After` within 60–3600 seconds, and successful sends are spaced by at least 60 seconds. Requests have a five-second timeout and do not follow redirects. The stable `Idempotency-Key` includes the source event or journal-entry identity, so repeated blocked or correction transitions on one PR remain distinct. A receiver can suppress duplicates if the process stops after an HTTP success but before saving its cursor. The sender is at least once across that narrow crash window; configure the receiver to deduplicate by this key. The local seen-key window is bounded to 2,048 transitions. Each scan reads at most 100 events and rotates through at most 100 decision files; delivery supports up to 10,000 retained decision journals.

`python3 -m ermik --config config.json status` fetches ready issue numbers from the configured GitHub repository and combines them with a local SQLite snapshot. It requires `gh` authentication. The snapshot does not change state; the command fails if GitHub is unavailable.

`status_snapshot(state_dir, max_parallel=..., ready_issues=...)` can be called without network access. When verified external queue numbers are not supplied, `queue.count` and `queue.ready_issues` are `null`, not zero. Output includes issue and PR numbers, job state and update time, occupied slots, selected and result models, attempt counts, retry time, provider cooldowns, and recent events. Raw errors, task content, branches, SHAs, logs, and local paths are omitted. The job list is capped at 1,000; `jobs_truncated` marks truncation, while aggregate counts cover every row. The limits are 1,000 ready issue numbers, 100 events, and 32 cooldowns.

Events and attempt counters persist in SQLite. `attempts.total` counts retry state records, not every worker invocation ever made; use `jobs[].attempts` for a particular job. For a pending PR, `jobs[].next_review_at` is the next poll time and `next_retry_at` is the next execution retry. `usage` sums token counts and indicative `estimated_cost` by provider and model, and separately counts attempts without complete usage data. These are neither subscription balances nor billed totals. A provider cooldown is a local retry time, not a guarantee that external quota has recovered.

Optional `quota_sources` read only the installed local Kimi Code or OpenCode server on `127.0.0.1`. Run `python3 -m ermik --config config.json quota-refresh` to record bounded percentage-used observations, then `quota-status` to read that same private snapshot without contacting a provider. The status command and dashboard read this file too. Each row identifies its source, observation time, unit, quota window and reset time; missing endpoint, authentication failure, rate limit, malformed response and stale data show `unknown` or `stale` with no retained values. The file expires for display after 15 minutes. These counters are observations, not a subscription balance, billing amount, or permission to exceed a configured route budget. Refresh is explicit; a separate scheduler may call it if desired. No worker container receives the local server token.

Each job also has bounded `reason_code`, `last_recorded_action`, and `next_action` fields. Confirmed worker authentication exit 77, exhaustion of all attempted provider routes after quota exit 75, and a failed local check command persist distinct reason codes. `broker_unavailable` means the controller could not connect to the broker before sending a request; inspect the broker manually. It does not identify why the broker failed to start. `publication_unconfirmed` means a PR request was attempted but its outcome is unknown; inspect the exact remote branch and PR and let controller reconciliation gate any further write. `publish_credential_unavailable` means the configured fork credential was absent before push; verify the credential manually. A blocked job with an unknown cause calls for manual reconciliation of the Issue, branch, and PR; the status command never recommends retrying an ambiguous write. A scheduled retry waits for the controller's reconciliation, including provider-capacity waits. A local `awaiting_review` record with a PR number asks the maintainer to verify the current remote HEAD before review. These fields come from local state only: a PR number is not a live identity check, and no HEAD is displayed without remote verification. Unknown failure causes stay `requires_inspection`; raw errors and provider responses are never classified by matching their text. The optional dashboard displays the same fields through a strict allowlist of reason, status, and action combinations.

`resource_guard(workspace, state_dir=..., min_free_bytes=..., max_worktrees=...)` checks free space under both configured roots and the active checkout count. The controller calls it before claiming a new issue, using `min_free_gb` and `max_parallel` from configuration. Clean, registered worktrees for published or merged jobs remain stored until [explicit bounded cleanup](storage.md); they do not consume an active slot. Interrupted, modified, unregistered, or unexpected-path worktrees remain for investigation and count against the worktree limit. Low free space under either root keeps the new issue queued. This check does not reserve disk space.

`log_window_metadata(path, max_bytes=...)` returns the size, truncation flag, and SHA-256 of up to the last 64 KiB of a private log without exposing its text. Captured container output is limited to 1 MiB; output beyond that limit is not retained in full. Raw check logs remain under the private `state_dir/ci-logs/` directory.

## Optional local dashboard

Run from the source checkout:

```sh
python3 -m ermik --config config.json dashboard --port 8765
```

Open `http://127.0.0.1:8765/`. JSON is available at `/api/status`. The page is read-only and refreshes every 10 seconds. GitHub queue data is fetched at most once every 60 seconds; a read failure returns 503. It shows queue and job states, occupied slots, selected and result routes, attempts, usage observations, cooldowns, and recent events. It does not show a verified remaining subscription balance. Issue text, errors, branches, SHAs, logs, local paths, and secrets are omitted. Responses are bounded and use `Cache-Control: no-store`.

The server binds only to `127.0.0.1` and accepts `Host: 127.0.0.1` or `localhost`. It has no authentication, so use it only on a trusted host; other local processes may reach it. Remote viewing needs a separately configured secure channel. Closing the command stops the page without affecting the controller.

## Optional maintainer queue

On the separate maintainer installation, run `python3 -m ermik --config config.json maintainer-queue` for JSON, or `python3 -m ermik --config config.json maintainer-view --port 8766` and open `http://127.0.0.1:8766/`. The page and `/api/queue` show the same projection as the CLI. Both fetch ready and blocked Issues, including those without a PR, plus open PRs from GitHub on each request. Each listing reads only up to the display budget and one overflow item; an oversized queue or remote failure does not reuse an old snapshot. The page refreshes every 120 seconds; each request still reads GitHub without a persistent cache. In a one-PR disposable trial on Windows, the current-evidence CLI took 26.15 seconds and `/api/queue` took 20.52 seconds. These measurements do not establish latency for larger queues or other hosts. The view binds only to IPv4 loopback, rejects nonlocal Host headers and write methods, and has no authentication. A remote operator must provide a separate secure channel.

Each row separates the remote Issue state label from controller runtime, which is **unverified** on the maintainer host. The route label comes from the verified remote Issue; the model reference is a bounded **publisher claim** from current evidence, when available. Neither is an observed running process. Exact HEAD appears only after the review packet checks remote identity twice. Evidence and check claims are separate from the maintainer's local exact-HEAD review; missing, stale, or unavailable evidence never appears as passed. A stale review after a correction asks for review of the new HEAD. Ambiguous identity suppresses the Issue number, HEAD, route, and model claim and asks for manual reconciliation. The view offers guidance only; it cannot admit, request changes, execute, or merge.
